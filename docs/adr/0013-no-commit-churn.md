# ADR-0013 — One approved unit of work = one commit

Status: accepted

## Context

Iterative debugging often produces commit churn — `feat: x`, `fix x
attempt 2`, `WIP`, `tweak`, `more fixes`. The git log becomes
illegible, code review becomes harder, release-please's automated
changelog becomes noise, and rollback granularity is destroyed.

## Decision

One approved unit of work = ONE commit.

### Forbidden patterns

| Pattern | Why forbidden |
|---|---|
| `feat: x` then `fix x attempt 2` | circling — squash before commit |
| `WIP` / `tweak` / `more fixes` | not a unit of work |
| Same scope/type/description repeated | the unit was not actually finished the first time |
| Fix-up commits after PR feedback | amend or rebase; keep one commit |

### Iteration discipline

- Edit + test + lint locally until green.
- Then commit ONCE.
- If you discover a missing piece mid-work: finish the current unit,
  commit, open a new issue/branch for the next unit.

### Conventional commits

Every commit follows `<type>(<scope>): <description>`:

| Type | Use |
|---|---|
| `feat` | new functionality |
| `fix` | bug fix |
| `docs` | documentation only |
| `refactor` | code change without behaviour change |
| `test` | tests only |
| `chore` | tooling / build / config |
| `perf` | performance improvement |

If you find yourself writing the same `feat(probel-sw02p): cmd 03
connect` twice, you are circling — the first commit was incomplete.

### release-please

`CHANGELOG.md` is generated by release-please from commit messages on
main. Hand-editing the changelog is forbidden.

## Consequences

- Git log is readable and reviewable.
- Each commit is a coherent rollback unit.
- Code review is easier (one diff per concept).
- Automated changelogs are clean.

## Forbidden

- Multiple commits for the same scope/type/description across one
  branch.
- `WIP` / `tweak` / `fixup!` commits landing on `main`.
- Hand-editing `CHANGELOG.md` (release-please owns it).
