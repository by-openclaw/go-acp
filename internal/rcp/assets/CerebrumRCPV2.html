Note this is an initial beta release of the protocol and subject to change

  • All device values which can be obtained using HTTP GET commands can also be optionally received via the websocket back-channel, using the subscribe and unsubscribe URIs.

  • On subscribing to a URI, it's initial value will delivered. As such it is not envisaged that there should be a need to both GET and subscribe to a specific object.

  • When connecting the websocket, the token obtained during login will need to be provided (details to follow)

  • If the websocket is closed, all associated subscriptions will be dropped

  • All packets sent over the websocket will have the same structure as the related get response, but with a wrapper around them to give the context of the data

  • In order to improve throughput the /batch endpoint can be used. I haven't got a good schema for this yet so see https://developers.facebook.com/docs/graph-api/batch-requests for an idea of where this is going

  • The longer term intention will be to support HTTP2 and multiplexing, but batching may still be useful to allow multiple operations to arrive at the service concurrently

  • We will try to avoid creating 'combined' request type endpoints (set many objects at once) - batching should be used for this if needed. The assumption is the overhead of the batching should be minimal on modern HW. Routing is likely to be an exception where cross level takes are very common

  • In Version 2, subscription are created using the Backchannel rather than via the REST API
