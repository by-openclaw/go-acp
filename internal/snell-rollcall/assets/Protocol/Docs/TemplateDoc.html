The Basic Idea

You are trying to make a text file, called a template or .TPL, which can be used by the RollCall PC Software Suite to present the user with a GUI to control your box, even though the box may not have been around when the Software App itself was written.

The GUI consists of 1 or more pages, each containing Windowsy controls like buttons, scroll bars etc.  You need to specify the layout of the controls, how they should appear to the user, and which functions of your box they should affect, (via the RollCall commands and menus already defined for your box).

To provide the 2D layout of pages, we currently use AppStudio or DevStudio, included in various Micro$oft development suites, designed for editing Windows dialog boxes.  This gives you a drag and drop 2D size'n'position editor.  All the other parameters are defined by the text "caption" field in the editor.  It is important to note that the type of control visible in the template, (e.g. scrollbar or radio button), is also defined purely by the text in the caption field, and not by the AppStudio control type that you create. 

The template design process using App/DevStudio is not ideal, and better design tools are intended for the future!  If you are interested in using or contributing to future design tools, please contact Maurice.

Some rules

  • The page structure is flat, not nested.
  • If you have >1 pages, page 0 must contain a page list box, and all other pages must have empty space in the same place.
  • All pages must be the same total size in pixels.
  • A command must be mentioned in the menus, and not hidden, for its controls to appear in the template.
  • Pages mentioned in the page list box must be present in the template unless always hidden.
  • For clients to find your template automatically, it should be called "TEMPLATE.TPL", pkzipped in "TEMPLATE.ZIP", and exposed as a RollCall file.

Some hints

  • Design your menus against your template as well as a shoebox.  Not all things that happen to work on a shoebox will neccessarily make sense to a PC!
  • User interface should be designed around the Commands, not the menu structure, if the interface is to work well on both the front panel and the PC.
  • Don't make the pages too big - continously scrolling around on a low-res display is boring.
  • Look at some existing templates to get an idea of visual style for consistency.
  • Use cut and paste lots from an existing template to get going.
  • Cut and paste all 4 bits for a scrollbar together: Scrollbar, Number display, Preset button, surrounding Group box.
  • Keep an information pane, (same as shoebox left window), to the right of the page list box on each page.
  • Use group boxes to separate functional blocks.  N.B. they are purely visual, (i.e. they do not specify heirarchy).

Hiding and disabling

Disabling

Things can be dynamically disabled or enabled by the server, (the product being controlled).  On a shoebox, disabled things are visible in the menus, but do nothing when you push the buttons.  On a PC, disabled things are "greyed out".

Hiding

Things can be dynamically hidden or un-hidden by the server, (the product being controlled). On a shoebox, hidden things do not appear in the menu  On a PC, hidden things do not appear in the template pages.

What is a "thing?"

  • Individual RollCall menus can be hidden or disabled.
  • On a pure menu browser, (e.g. shoebox), this has the obvious effect.
  • On the PC, all controls are attached to command numbers, not menu lines.  The template controls will take the state, (active, disabled or hidden), from the menu line(s) with matching command number.
    For example, consider a menu line called "NTSC Hue" which adjusts the value of command number CM_HUE.  On the template, there are 4 items, (ScrollBar, Preset Button, Display Text, Bounding Group Box), all of which are bound to CM_HUE.  When not in NTSC mode, the unit disables the hue menu line.  On the shoebox, this causes the action icon, ("<"), to dissappear from the menu line, and the menu line doesn't action when pressed.  On the PC, the 4 template items are shown "greyed out"
  • A complete template page can be hidden, but not disabled.  See CM_PAGELIST definition

Basic syntax

Text,CommandNumber,CommandValue,ObjectType

I.e. 4 comma separated fields.

Generally, the Text field is what will be displayed on the screen, and can include the special substitution strings explained below.

The CommandNumber can be numeric or, more usually, the string token #defined in a .H file somewhere.  0 is a valid command number, so -1 should be used to indicate "no command number".

The CommandValue corresponds to FUNC_STR.rMinRange for button objects, and is related to rValue in the FUNCSTATUS_STR.

The ObjectType defines which GUI control will be displayed, e.g. scroll-bar or check box. There are two sets of control types, those specific to templates, and those equivalent to the menu style flags defined for FUNC_STR.rStyle.  N.B. a command number can be bound to many controls, of different types.  For example, a command number with a single menu line of, say, CM_NUMBER menu style can be bound to a scrollbar, and a read-only display, and a preset button, etc.

Fields listed as "Not used" in the table below should be filled with a zero, except command numbers which should be set to -1.

Syntax for CM_PAGELIST control

"p0=u0[^c0]:p1=u1[^c1]:p2=u2[^c2] [...],-1,0,CM_PAGELIST"

Page n is specified by

  • pn is the textual page name shown in the list box.  When the user chooses this entry in the list box, the template numbered n will be displayed.
    This text string is also used by the template compiler to convert textual dialog names to page numbers.
  • un defines which user levels see this page.  The value is a bit flag sum of 1,2,4,8 for user, engineer, supervisor, and factory respectively, in decimal,  E.g. value 15 means that the page is visible at all user levels, but value 12 is hidden at engineer or user access.
  • ^cn is optional.  If present, it binds the page to a command numbersomething.  The page visibility then follows the same rules as other controls bound to a command numbersomething, allowing the whole page to be hidden by the server.

    The full syntax for ^cn looks something like this: ^$[x]yz, where

    • y specifies which bit of the menu line FUNC_STR you want to match to:
      • S1 - szText
      • S2 - szParamString
      • c - rCommand
      • i - rMenuIndex
      • m - rMinRange
    • z is the value to match against.
    • x (optional) is the occurence count for the match, defaulting to 1.
    But there are some short-hands - see examples below.
    In RollCall.EXE 3.1, any non-command number binding would only match partial menu lines.  In RollCall.EXE 3.2beta 27.5.1999 or later, the binding now matches any menu line, partial or not.

Example page list

"Control=15:Optional Features=15^12345:Silly Features=12^$5S1Silly:Factory=8,-1,0,CM_PAGELIST"

This defines 4 pages:

  • Page 0 is named "Control", and is always visible at all user levels.
  • Page 1 is named "Optional Features", and is visible at all user levels except when command number 12345 is hidden,
  • Page 2 is named "Silly Features", and is visible at factory and supervisor levels except when the 5th menu line found to have string name "Silly" is hidden,
  • Page 3 is named "Factory", and is visible only if connected at factory user level,


Text substitution strings

Code Replaced with
$S1 Current string name of RollCall Menu item, i.e. FUNC_STR.szText
$S2 Current format string of RollCall Menu item, i.e. FUNC_STR.szParamString
$V String representation of RollCall Command Value, i.e. string value if returned by server, or number value, (FUNCSTATUS_STR.rValue), printf formatted with FUNC_STR.szParamString



Template compilers

Template compilers

.RC to .TPL compilation

A recent template compiler is rctran2.awk.  (Look in source code to see RCS revision.)

Typical use: Use the wonderful M$ App/DevStudio to design "dialogs" or template pages, then use this awk script to convert the .RC source file to the .TPL file as used by RollCall.EXE.

Recent new features: Dialog page names now take the form ID_ii_cc_uu_pagename where
ii is the RollCall ID
cc is the RollCall Cmd Set version
uu is the set of userlevel bits
pagename is either 0 for the first page, or a string which will be matched to the page name in the list box on the first page.  (Spaces in the page name should be replaced with "!" characters in the dialog name.)

Example dialogs: Dialog ID_99_1_15_0 contains a list box with caption
Control=15:Genlock Mode=15:Setup=15,-1,0,CM_PAGELIST.  Dialogs ID_99_1_15_GENLOCK!MODE and ID_99_1_15_SETUP will get compiled to pages 1 and 2 respectively, to match their position in the list box.

.RC to .RC pre-processing

A recent template expander is rcexpand.awk.  (Run with no parameters to see RCS revision.)

Typical use: Maintain a single .RC source file covering multiple products in a shared project. A single dialog page can be used as one or more template pages across different product IDs and command set versions.

The basic feature of rcexpand is to use dialog names like ID_28.63.64.65_1.2_15_0.  This single maintainable source dialog will get expanded to target IDs 28, 63, 64 and 65, at both command set versions 1 and 2. 

#makefile snippet
expanded.rc :   $(RCEXPAND) myproj.rc rcexpand.txt
   $(AWK) -f $(RCEXPAND) myproj.rc @rcexpand.txt 

#rcexpand.txt
#This puts all the IDs in one output file
#You can put different IDs in different output files
28:expanded.rc
63:expanded.rc
64:expanded.rc
65:expanded.rc
119:expanded.rc
It is also possible to use tag substitution in dialog names.  E.g. you can define a tag 
ALLVER;0.1.2.3
and then name a dialog ID_23_ALLVER_15_Genlock.  This will get expanded to all the listed command set versions.

TPL File Format Notice: This information is intended for developers of template design tools.  To use any of our template design tools to develop templates, it should not be neccesary to be familiar with this information!

TPL File Format

The TPL format appears similar to the DOS/Windows ‘.ini’ file format consisting of section headers of the form:
[section]
and name/value list pairs within these sections of the form
Name=Value,MoreValue,AnotherBit

It must however be noted that, whilst the order of lines and sections within windows ini files is supposedly variable, TPL files are parsed sequentially and should be created in the order specified in this document.

Note: A template file may contain templates for multiple product command sets.

Sections

Two types of section are defined: Version and templatepage.
Version is simple: the section header is

[Version]

and the only Name/Value pair currently used is
Version=value
where value is a positive integer. However the tool chain is being changed to support date-stamping based on the original file date, with this information held on a per-ID and CommandSet in this section.
Only one Version section is permitted in a file.

The templatepage section contains most of the file data. Multiple templatepage sections are permitted, one for each page of the Rollcall template. The section header is of the form:

[TemplatePage]

This takes the form of: [Device_ID:CommandSet_Version:Userlevel_Flags:Page_Number]
Each of these is a non-negative integer.
  • Device ID is the Rollcall ID specified for the product.
  • CommandSet_Version is the RollCall ComandSet Version specified for the product.
  • Userlevel Flags is a 4-bit bitmask specifying whether the page is visible in User, Engineer, Supervisor and/or Factory userlevels.
  • Page Numbering starts at 0. Pages should be consecutively numbered but need not be in order (although this makes the files easier to read manually).
eg: The MFXNRS TPL file has the first page header [179:1:15:0]

Within the templatepage section the following Name=Value sets are permitted, and should be present in the order specified:

Size= Left,Top,Width,Height
(required, one only per section, should be identical for each page)
Each field is an integer, counted in pixels from the top left corner.

Ctlnumber=Name,Command,Value,Type,Left,Top,Width,Height
Multiple allowed but number should never be the same for two Ctl lines within one templatepage section. number should start at 0 and be consecutive and ordered.

Page 0 of the template should contains a PAGELIST item detailing the names and visibility of all pages in the list. The Name field of this item matches the syntax of the first section (ie p0=u0[^c0]:p1=u1[^c1]:p2=u2[^c2] [...]) of the CM_PAGELIST control used in the resource files; please see the document Template Controls for full information.
PAGELIST items on subsequent pages within the same template are discouraged and will be ignored. A file of multiple templates may however contain multiple pagelists.

For all other controls, Name is a simple text label of alphanumeric characters and spaces, or simply the digit ‘0’ if no label is required.

Most (if not all) pages tend to contain a special block allowing the device status to be displayed:
Ctl1=Unit Status,-1,0,-1,84,8,128,52 (this string is free text)
Ctl2=INVISIBLE,0,0,-15,98,21,100,8
Ctl3=INVISIBLE,1,0,-15,98,29,100,8
Ctl4=INVISIBLE,2,0,-15,98,37,100,8
Ctl5=INVISIBLE,3,0,-15,98,45,100,8

It appears that the 'INVISIBLE' strings are replaced with text showing the device status on each page, usually to the right of the pagelist.

For all controls, all fields except Name are integers, as follows:

  • Command is the Command number corresponding to the control, or -1 if no command applies. The Command number -1 is always considered to be unhidden and enabled.
  • Value is the rMin binding for Radio buttons, and a style specifier for some of the text-display fields. Usually set to 0 if unused.
  • Type is the numeric value of the control type.
  • Left,Top,Width,Height are as specified in ‘Size’ above, and specify the placement of the control.
SaveSet=Command,Command,Command
Multiple allowed, only permitted in the first page.
This is a list of commands that will be saved and restored by the Rollcall control application in the precise order given in this file. Multiple SaveSet lines will exist, each with up to 10 commands listed, and will be concatenated to give a full list.
