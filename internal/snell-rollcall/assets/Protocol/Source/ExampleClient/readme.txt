RollCall Test Client Usage Instructions
=======================================

Description
-----------
This is a very simple test client that exercises the main client-side interactions for the RollCall menu and control services.
It uses the blocking variants of the menu and control clients to simplify the user API, and connects to a target network via
RollCall over IP (IpShare). It runs as a console utility that the user can interact with via the command line.

It is useful as an illustration of how to create a minimal client application, since:

- the StartRollCall() function shows the minimum set of API calls to get the RollCall library up and running
- the various client APIs that an application might need (eg get or set a parameter) are exposed via command line interface
- since it includes the RCV2 message tracing module, it is possible to analyse the messages generated by typical client actions

Note that this is not a polished user application, and doesn't include much (any!) checking of user arguments. So it is quite easy
to crash by omitting arguments for command line controls....

Finally, this client now includes an illustration of how to write client code using the asynchronous (non-blocking) control client.



Building the project
--------------------
The project relies on the RollCall V2 library only



Debugging the project
--------------------------------
Before debugging the project, you need to set the project command arguments to the IP address and port of the network that
you intend to connect to. The standard port will be 2050. For example, "172.19.81.40 2050".

Equivalently, if you run the executable (ie not using Visual Studio), then the command would be
  	"rolltestclient 172.19.81.40 2050"
  	
  	

Usage
-----

Once you have run the program and it has connected to the network, you can then make a menu and control connection to a target unit.

All commands are simply typed into the console, with appropriate response / debug information printed back to the console.


The commands available (in the rough order that you might want ot try them) are as follows:

	connect nnnn:uu:pp			Connect to the unit at RollCall addresss nnnn:uu:pp, where nnnn is network, uu is unit, pp is port
								A typical address for an IQ frame or Alchemist might be 0000:20:00,
								whereas a typical addresss for a module in a frame would be 0000:20:05
								Translates into an SP_CALL message and SP_ACK response
								
	getparam cmdnum				Read the value of the specified parameter, eg getparm 16469
								Translates into an SP_GETFSTAT message and SP_RETFSTAT response
	
	setparam cmdnum mode val	Set the value of the specified parameter. Mode = 1 for numeric, 2 for string.
								Translates into an SP_SETPARAM message and SP_RETFSTAT response
	
	bcready val					Set the Back Channel ready state to value. 1 = enable, 0 = disable
								Translates into an SP_BKCHNREADY message and SP_ACK response
	
	repchanges val				Set Function Change reporting (Control values) state to value. 
								In theory function change reporting can be enabled/disabled per individual command,
								but in practice most clients set value to 0xFFFF to mean "all commands".
								Translates into an SP_REPFCHG message and SP_ACK response
	
	reqmenu	idx					Request menu set starting at base line index idx, ie find out how manu menu lines exist starting 
								at this base. When retrieving the entire menu set for a unit, the starting point is to request
								the menu set for line 0.
								Translates into an SP_GETFUNC message and SP_BLOCKHEADER response
	
	loadmenu idx				Get menu line at offset idx from base set by reqmenu.
								If no lines are already cached by the client, then the client would normally sequence through
								every offset idx from 0 up to (count - 1), where count is value returned by reqmenu.
								Translates into an SP_GETNEXTPKT message and SP_RETFUNC response
	

There are also some example functions for reading the parameters from a 5915 audio input node on an S800 router. One uses the
synchronous (blocking) client, while the other uses the asynchronous (non-blocking) client. 

Note also that the async client relaxes RollCall's normal strict end-to-end acknowledgement on the particular client session,
which provides a big performance improvement on WAN links where the latency may be measureed in tens of milliseconds.

  	
It is also possible to enable message tracing of the RollCall message flowing back and forth. The message tracing uses a simple
circular bufer to store the last N messages in memory (where N is set to 4096 for the test client).

There are various modes to this:

	live on	| off				enables or disables 'live' message tracing to the console
	
	trig						triggers message capture, ie stops further messages being added to the trace history
	
	restart						restarts message capture, clearing down any messages previously recorded
	
	list						prints all messages in the buffer to the screen
	
	list N						prints last N messages to the screen
	
	dump filename				prints all messages in the buffer to the filename
	
	
	
The format of messages is as follows

  563.483000  Tx TestClient 0000-FF-00:FF => 0000-00-00:FF  33:SP_IAM           F=00 L=40  >00 03 00 00 FF 00 00 FF 00 00 01 E3 01 00 20 01 .............. .
                                                                                          54 65 73 74 43 6C 69 65 6E 74 00 CD CD CD CD CD TestClient......
                                                                                          CD CD CD CD 00 00 00 08                         ........

where the fields in order are:

	timestamp, eg 563.483
	direction, eg Tx
	Physical Interface, eg TestClient
	Source address, eg 0000-FF-00:FF
	Destination address, eg 0000-00-00:FF (all zeros shows that this is a broadcast)
	Message number and type eg 33:SP_IAM
	Flags,  eg F=00.  The key flag is back channel, ie F=80 => back channel, F=00 => front channel
	Length, eg L=40. The length of the message payload, ie excluding standard headers and packet flags

followed by the payload bytes shown in hex and in ASCII, with 16 bytes per line

		

Typical Client Connection Sequence
----------------------------------

For a typical client such as the standard RollCall Control Panel application, the connection sequence is as follows:

		Client							Server
		-----							-----
			
			---------- SP_CALL -------->
			<--------- SP_ACK  ---------

			---------- SP_REPFCHG ----->
			<--------- SP_ACK  ---------


			---------- SP_GETFUNC ----->
			<--------- SP_BLOCKHEADER --

			---------- SP_GETNEXTPKT -->
			<--------- SP_RETFUNC ------
	
						...	repeated as necessary (depending on which lines are already cached)

			---------- SP_GETNEXTPKT -->
			<--------- SP_RETFUNC ------

					repeated blocks of SP_GETFUNC and SP_GETNEXTPKT (according to menu structure) 		
						...		
						...
						...

			---------- SP_GETFUNC ----->
			<--------- SP_BLOCKHEADER --

			---------- SP_GETNEXTPKT -->
			<--------- SP_RETFUNC ------
	
						...	repeated as necessary (depending on which lines are already cached)

			---------- SP_GETNEXTPKT -->
			<--------- SP_RETFUNC ------


			---------- SP_BKCHNREADY -->
			<--------- SP_ACK  ---------



			---------- SP_GETFSTAT -->
			<--------- SP_RETFSTAT ---

						...	repeated as required by client for display of up-to-date parameter values

			---------- SP_GETFSTAT -->
			<--------- SP_RETFSTAT ---
  		
  		
  		
The above sequence shows only front channel activity. But at the point that the back channel is enabled (SP_BKCHNREADY),
then typically a server will send multiple back channel menu lines and display updates, eg

			<--------- SP_RETFUNC ------
			---------- SP_ACK  -------->

						...	repeated as needed by server to ensure client has up-to-date state of cached menu lines

			<--------- SP_RETFUNC ------
			---------- SP_ACK  -------->
