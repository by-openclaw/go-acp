# Cerebrum RouteMaster — what still needs the user interface: open points for provisioning over the APIs

**From:** BY-SYSTEMS SRL — integration team
**To:** EVS Cerebrum support
**Date:** 2026-10-22
**Server tested:** Cerebrum 2.9.3 build 15692, web client 2.9.3 build 2222 (staging VM, 10.6.250.5), standalone; one comparison on a Cerebrum 2.9.0
**Documents used:** *Cerebrum Northbound API* v0.17 (October 2026); *EVS Cerebrum RCP* OpenAPI 2.6.1 (the server serves 2.5.3)
**Scope:** everything a RouteMaster needs to be provisioned from a plan without touching the user interface: levels, any router or IP device on a level, sources and destinations with their bindings, virtual pairs, categories, alternate mnemonics, routes. Federation is out of scope until our federation licence is installed. Tie lines and "make an existing IO virtual" are not needed by us and are left out.
**Method:** every line below was run on the server on 2026-10-22, read back over the same interface, and checked in the RouteMaster user interface. The two detailed notes of the same day (*Northbound API v0.17 — the RouteMaster messages measured on 2.9.3* and *RCP 2.5.3 — RouteMaster create, read, update, delete measured on 2.9.3*) carry every request and answer.

## 1. In one paragraph

Over Northbound and RCP we create, name, bind, categorise, route and delete the sources and destinations of the RouteMaster, local and virtual, and we name the levels. What we cannot do from either interface decides whether anything else works: a level's default device, its "Multiple Devices" setting and its IP filter exist only in the user interface, and without them the server acknowledges every IP binding and applies none. Added to that, 2.9.3 resolves an IP binding only in the form `NMOS|slot|node|name`, which no document states, did not migrate the bindings 2.9.2 had stored, and answers `ACK` / `202` to names it will never resolve. The table lists the points in the order in which they block a provisioning run.

## 2. Open points

| # | Topic | What we need to provision without the user interface | Northbound today | RCP today | Status |
|---|---|---|---|---|---|
| 1 | Level: default device, "Multiple Devices", IP filter | A message or resource that sets, for a level, its default device (the IP Router, or a router), the "Multiple Devices" flag when IP senders and router inputs share the level, and the IP filter; and the read of it | no message. `LEVEL_MNE` names the level only; `RM_DEFAULT_DEVICE`, documented in the `LEVEL_MNE` reply (§5.1.4), is never sent, not even for the two levels configured in the user interface | no write: `PATCH` / `POST` / `PUT /routemaster/levels` answer `404` Unknown RouteMaster collection; `PATCH /devices/Cerebrum/0/routers/level-mnemonics/{id}` accepts the fields with `200` and drops them | **open — blocks everything**: a level created by the API resolves no IP binding until the user interface |
| 2 | IP binding name | The documented form of `TARGET_SENDER_NAME` / `TARGET_RECEIVER_NAME` and of `senderReceiver`, and an error when the name does not resolve | only `TARGET_SENDER_NAME="<node>\|<sender>"` with `SUB_DEVICE="<slot>"` resolves, stored as `NMOS\|slot\|node\|name`; `"VTX-01"` alone is stored, returned and unresolved; both answer `ACK` | only `senderReceiver: "NMOS\|slot\|node\|name"` resolves; the bare name 2.9.2 stored is unresolved; both answer `202` | **open — silent**: a wrong name is accepted and the destination never routes |
| 3 | Bindings at upgrade | The bindings stored by 2.9.2 migrated to the 2.9.3 form at installation, or a release note | after the 2.9.3 installation every level had lost its device and every binding of the plant (24) was stored in the bare form and unresolved; we rewrote them all | the same | **open**: an upgrade silently breaks the plant's IP routing |
| 4 | Acknowledgement means applied | A `NACK` / error when an association, a route or a mnemonic cannot be applied (level without device, unresolvable name, slot beyond the defined names), or a completion signal | `ACK` in every such case; `RESULT ACCEPTED` means validated and queued | `202` in every such case | **open**: a client cannot trust an answer without a read-back |
| 5 | Created ids | The ids created by `RM_SRCE_ADD` / `RM_DEST_ADD` and by `POST /routemaster/sources` returned in the answer | `RESULT VALUE="ACCEPTED"` only; ids are positions, re-read by a wildcard `OBTAIN` | `202`, no id; `GET` before and after | **open**: unsafe with two clients |
| 6 | Level delete | A message to delete a level | `LEVEL_MNE` with an empty name: `NACK 8` | none | **open**: two test levels wait for the user interface |
| 7 | Level properties read | `GET /routemaster/levels` as documented in 2.6.1 | — | `404` on 2.5.3, which 2.9.3 serves | **open**: the document describes a server we do not have |
| 8 | Alternate mnemonic names | List, create and rename the alternate mnemonic names (the columns); a `NACK` for a slot beyond them | values by slot proven on sources, destinations, virtuals and levels once the names exist; no message for the names; a slot beyond them is acknowledged and dropped; only the `LEVEL_MNE` reply reveals how many exist | values by name proven; the names only in the user interface; a wrong name `400` | **open**: the names are a user-interface step |
| 9 | Association read-back | `ASSOCIATION_N` rows as §5.1.5 documents them for a bound source or destination | with the level configured the rows come with `RM_IP_UID` and `RM_TAGS`, but `RM_DEVICE_TYPE=""`, `RM_LEVEL_ID="0"`, the same port id `4026531837` on every row and no `RM_REVERSED`; with the level unconfigured, no element at all | the binding string is returned | **open — minor**: a client cannot tell a resolved binding from an unresolved one |
| 10 | Tags read | `OBTAIN RM_SRCE_TAGS` returning `LIST="Tag1\|Tag2"` as §5.1.7 documents | with the level configured `LIST="ZZ-PROBE,,,,"`: the tag, comma-delimited with four empty fields; with the level unconfigured `LIST=",,,,"` | the tags are returned | **open — minor** |
| 11 | Virtual flag | Whether a source or destination is virtual, in the `SRCE_MNE` / `DEST_MNE` reply | no attribute; only the empty association rows hint at it | `virtual` is returned | **open — minor** |
| 12 | Categories over RCP | A category resource | categories proven over Northbound (create, items, membership) | none | **open — low** for us: we use Northbound |
| 13 | Device apply time | A completion signal, or the time to expect | a route is applied on a Neuron receiver within 4 s of the `ACK`, on a FusioN receiver after more than 6 s; the crosspoint table lags the device | the same | **open — information**: a panel or a client that waits less falls back to the previous source |
| 14 | Register a router or an IP device on the server by API | `DEVICE_CONFIGURATION` (§4.3) measured on 2.9.3, or the documented alternative | not measured in this campaign | `POST /devices` not measured in this campaign | to measure — the next step once point 1 exists |

## 3. What works today, for the record

Over Northbound: `RM_SRCE_ADD` / `RM_DEST_ADD` local and virtual, `RM_*_DELETE`, `SRCE_MNE` / `DEST_MNE` / `LEVEL_MNE` names and alternate values by slot, `SRCE_ASSOC` to a router input (the Neuron registered as a router, "1 - IP001-01" in the user interface), `SRCE_ASSOC_IP` / `DEST_ASSOC_IP` in the `<node>|<sender>` form on a configured level, `RM_SRCE_TAGS`, categories, `ROUTE` on one level and on all levels. Over RCP: create, read, rename, delete, virtual pairs, bindings in the `NMOS|slot|node|name` form, tags, level rename. With the levels configured in the user interface and the names in that form, our plan provisions the plant's 12 sources, 16 destinations, 3 virtual pairs and 7 categories in one run, and a second run changes nothing.

Thank you for the two interfaces; point 1 is the one that keeps the user interface in every provisioning, and points 2 to 4 are the ones that let an error pass unseen. We are glad to re-run every line on any build.
